# ADR-0002: Phase 0技術検証の結果

- ステータス: 決定(Phase 0完了)
- 日付: 2026-08-13
- 決定者: gorihei

## 背景

ADR-0001でTauri 2.x + Rust + React/TypeScriptを採用することを決定した。REQUIREMENTS.md §17 Phase 0の指示どおり、実際に動くスパイクを作って主要な技術リスクを検証した。成果物は `app/` 以下のTauriプロジェクトに実装として残っている。

## 検証項目と結果

### 1. Tauriプロジェクト雛形

`npm create tauri-app` でReact/TypeScriptテンプレートを作成し、`npm run tauri dev` でデスクトップウィンドウが実際に起動・常駐することを確認した。

**遭遇した環境課題(このマシン固有)**:
- Visual Studio 2022 EnterpriseのMSVCツールセットに`msvcrt.lib`等が欠落しておりリンクエラー(LNK1104)が発生。VS2019 CommunityのMSVCツールセットは完全だったため、`app/.cargo/config.toml`でリンカー・LIB/INCLUDEパスを明示的に固定して解決した。
- 2026-08-22追記: VS2022の「C++によるデスクトップ開発」を再導入し、MSVC v143の欠落ファイルを復元した。VS2022環境だけで`cargo check`が成功することを確認したため、上記の`app/.cargo/config.toml`によるVS2019固定は廃止した。
- Bashツール経由でTauriアプリ(GUIプロセス)を起動すると、ビルドは成功してもウィンドウプロセスが直後に終了する現象を確認。PowerShell経由での起動では問題なく常駐した。原因は未特定(Git-Bash/MSYS2のプロセス生成まわりの可能性)だが、開発時はPowerShellから起動する運用で回避できる。

### 2. ConPTY(portable-pty) — FR-CLI-001, FR-CLI-002

`portable-pty` crateでPowerShellをConPTY起動し、xterm.jsで表示。日本語入出力(`echo こんにちは`)とANSI表示が崩れないことを実機で確認済み。UTF-8のマルチバイト文字がチャンク境界で分断されないよう、未確定バイトを次回読み取りへ持ち越す処理を実装した。

**結論**: 実装方針として問題なし。本実装ではタブごとのセッション管理・終了時のプロセス後始末(§19 未決事項#12)を追加する必要がある。

### 3. プラグインプロセスとIPC — FR-PLUG-007, §12.3

サイドカー実行ファイル(`plugins/sample-plugin`)を子プロセスとして起動し、改行区切りJSONでリクエスト/応答をやり取り。`crash` methodで意図的にパニックさせても、ホスト(Tauriアプリ本体)は継続して動作し、クラッシュをイベントとして検知、UIから再起動できることを実機で確認した。IPC呼び出しには5秒のタイムアウトを実装済み。

**結論**: プロセス分離によるプラグイン障害の封じ込めは実現可能。本実装では複数プラグイン対応・クラッシュループ検出(§11.2)・権限ブローカーとの連携が必要。

### 4. ダッシュボードグリッド — FR-DASH-001〜005

`react-grid-layout` v2でドラッグ移動・リサイズ・衝突回避(自動詰め)・localStorageへの永続化を実装し、実機で操作感を確認した。

**遭遇した問題**: react-grid-layout v2はv1からAPIが全面刷新されており(`WidthProvider`廃止、`compactType`/`preventCollision`が`compactor`オブジェクトへ再編)、ネット上のv1向け情報を鵜呑みにすると動作しない。`width`未指定でリサイズが縦方向のみになる不具合と、衝突回避が効かない不具合の両方を実際に踏んでから修正した。

**結論**: ライブラリの選定自体は妥当。本実装時はv2のAPIドキュメント(型定義)を直接参照すること。

### 5. グローバルショートカット・トレイ・通知 — §5.3

`tauri-plugin-global-shortcut`でCtrl+Shift+Hによるウィンドウ表示/非表示切替、`tauri`本体のtray-icon機能でトレイ常駐・右クリックメニュー(表示/終了)、`tauri-plugin-notification`でOSトースト通知を実装し、いずれも実機で動作確認済み。

**遭遇した問題**: `Shortcut`の`to_string()`表現(`"shift+control+KeyH"`)が登録時の文字列(`"Ctrl+Shift+H"`)と一致せず、ハンドラ内の比較が常に失敗する不具合を実装時に発見・修正した(`Shortcut`同士の`PartialEq`比較に変更)。文字列比較ではなく型の比較を使うべき典型例。

**結論**: 3機能とも実現可能。本実装では、ショートカットの競合検出(FR-LAUNCH-006)とトレイ常駐挙動の設定可能化(§5.3)が必要。

### 6. 高DPI・ウィンドウ位置復元 — §5.3

`tauri-plugin-window-state`を導入し、ウィンドウの位置・サイズを保存、アプリ再起動後に復元されることを実機で確認した。保存先モニターが存在しない場合はOS任せの配置になる実装のため、「画面外に復元される場合は可視領域へ補正する」要件も満たす設計になっている。`minWidth`/`minHeight`もtauri.conf.jsonに設定した。

**未検証**: 実機での125%/150%/200% DPI切り替え時の表示崩れは、検証環境の制約により目視確認できていない。Phase 3(ダッシュボード本実装)着手前に確認する。

### 7. SQLiteとシークレット保存 — §9.1, §10.2

`rusqlite`(bundled)でローカルDBへの読み書きを実装し、アプリ再起動をまたいで残ることを確認した。シークレットは`keyring-core` + `windows-native-keyring-store`でWindows資格情報マネージャーへ保存し、SQLiteファイルや設定ファイルには一切書き込まれないこと、実際にコントロールパネルの資格情報マネージャーに登録されることを実機で確認した。

**設計判断**: `keyring`メタクレートではなく`keyring-core` + `windows-native-keyring-store`を直接使用した。`keyring`クレート自身のドキュメントが「特定プラットフォームの実装を制御したいアプリケーションは`keyring-core`と必要なストアだけに直接依存すべき」と明記しており、`keyring`の`v1`互換フィーチャーを有効にすると全プラットフォーム分の依存(Apple/Linux D-Bus等)が不要に増えるため、Windows専用の本アプリには適さないと判断した。

**結論**: 実現可能。本実装ではDB側のマイグレーション機構(§9.4)とシークレット参照モデル(プラグインへは値でなく参照を渡す: §10.2)を追加する必要がある。

## 性能測定

測定環境: 本マシン。測定対象はリリースビルド(`cargo build --release`、`app.exe`単体実行、インストーラー化はしていない)。

| 指標 | 目標(§11.1) | 実測値 | 判定 |
|---|---|---|---|
| コールド起動からメインウィンドウ表示まで | 3秒以内目標・5秒以内許容 | **0.77秒** | ◎ 目標達成 |
| `app.exe`自体のアイドル時メモリ(WorkingSet) | 300MB未満目標 | **44.8MB** | ◎ 目標達成 |
| `app.exe`自体のアイドル時CPU(10秒平均) | 平均1%未満目標 | **0%** | ◎ 目標達成 |

### 重要な注意点: WebView2ヘルパープロセスの扱い

`app.exe`自体は上記のとおり非常に軽いが、Tauri(WebView2)アーキテクチャでは`msedgewebview2.exe`が別プロセスとして最低6つ程度自動的に起動し(Chromiumのマルチプロセスモデルによるブラウザ/GPU/レンダラー/ユーティリティプロセス群)、実測でこれらの合計WorkingSetは**約389MB**だった。

- `app.exe`単体: 44.8MB
- `app.exe` + WebView2関連プロセス合計: **約433MB**

§11.1の「コア常駐メモリ300MB未満」は「ターミナルやプラグイン子プロセスを除く」という除外規定のみで、WebView2自体は除外されていない。これはWinUI 3(ネイティブレンダリング、ブラウザエンジン不要)を前提に書かれた数値目標だった可能性が高く、Tauri採用によって生じた新しいトレードオフとして扱うべきである。

**決定(2026-08-13)**: §11.1の「コア常駐メモリ300MB未満」は`app.exe`単体を対象とし、WebView2ヘルパープロセス群は対象外と明記する形でREQUIREMENTS.mdを更新した。個人利用前提であり、WebView2込みの実消費(約433MB)も許容する、とユーザーが判断した。

## 結論

Phase 0で洗い出した技術要素はすべて実現可能と確認できた。個々のライブラリ選定(react-grid-layout, tauri-plugin-global-shortcut, tauri-plugin-window-state, keyring-core等)は§12.1(ADR-0001)の内容を実装で裏付けるものとして確定する。§19未決事項の#2・#3はADR-0001で既に決定済み。

Phase 1(コアシェル)着手前に対応すべき既知の宿題:
- 高DPI(125%/150%/200%)での目視確認
- Bash経由でのGUI起動が失敗する原因の切り分け(開発ツール側の制約なら記録のみで良いが、CI等で自動テストする場合は要対応)
- プラグインのサイドカーバンドリング(`tauri.conf.json`の`externalBin`)の本実装
